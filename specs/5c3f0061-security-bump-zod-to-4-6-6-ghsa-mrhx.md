# Security: bump zod to 4.6.6 (GHSA-mrhx-c7xc-m3w5)

**Type:** feature

Automated maintenance. zod is a direct dependency (package.json dependencies, "^3.24.1", locked at 3.25.76). The osv scan reports GHSA-mrhx-c7xc-m3w5 (high, memory exhaustion validating oversized constrained collections), fixed in 4.6.6. Change the zod version in package.json to exactly 4.6.6. App behaviour must not change. Both scanner findings are the same advisory on the same locked zod, so one version change clears both. The lockfile is not hand-edited and must be regenerated with `pnpm install`.

## Acceptance criteria

- **AC-1** Given package.json, when the change is applied, then dependencies.zod is exactly "4.6.6" and no other dependency version, script or field in package.json changes.
- **AC-2** Given pnpm-workspace.yaml, when the change is applied, then it is unchanged, unless an existing pinned zod entry exists (none does at present). No overrides entry is added because zod is a direct dependency.
- **AC-3** Given the lockfile, when `pnpm install` is run after the change, then pnpm-lock.yaml resolves zod to 4.6.6 and no zod@3.25.76 entry remains. The lockfile is regenerated by pnpm and not hand-written.
- **AC-4** Given the zod 3 to 4 major upgrade, when the code is built, then the only source edits are mechanical changes needed to compile and behave identically under zod 4. The known case is src/steps/defs.ts, where `z.record(z.unknown())` (two uses, line 23) becomes `z.record(z.string(), z.unknown())`. Validation messages, rules and error handling stay the same.
- **AC-5** Given the existing checks, when the CI verify job runs (db:migrate, lint, typecheck, test, build), then all pass without changes to tests, except a purely mechanical test edit that zod 4 strictly requires.
- **AC-6** Given the business rules in docs/business (for example BR-CLI-1, BR-QUO-2, BR-PRC-1, BR-JOB-11), when the upgrade is applied, then none of them change, and neither do the validation limits or messages they describe.

## Edge cases

- This is a major version jump (3.25.76 to 4.6.6). Places that may behave differently under zod 4 are `z.record` with one argument, `.default()` typing, `.passthrough()` (deprecated but still works) and `instanceof ZodError` checks in src/actions/shared.ts and app/api/it/scan/route.ts. CI typecheck and tests must confirm these.
- The lockfile has peer-dependent entries (@anthropic-ai/sdk, openai, zod-validation-error and kit packages) that accept zod ^3.25 || ^4. They should resolve to the root zod 4.6.6 after `pnpm install`. If any zod 3.25.76 entry remains in the regenerated lockfile, the follow-up is an override `'zod@<4.6.6': ^4.6.6` in pnpm-workspace.yaml, commented with the parent package and GHSA-mrhx-c7xc-m3w5.
- pnpm minimumReleaseAge may block a very recent release. If `pnpm install` refuses 4.6.6 for that reason, add `zod@4.6.6` to minimumReleaseAgeExclude. This is not done up front because no zod entry exists today.

## Business rules

- `docs/business/sales.md` (unchanged): Validation limits for clients, quotes and the price list (BR-CLI, BR-QUO, BR-PRC) - Zod schemas keep the same constraints and messages.

## Out of scope

- Any other dependency update
- Refactoring to zod 4 idioms or removing deprecated zod APIs that still work
- Hand-editing pnpm-lock.yaml
- Changes to CI, workflows, migrations, access rules, payments or deployment settings
- Adding an overrides entry, unless the regenerated lockfile still contains zod 3.25.76

## Affected areas

- package.json
- pnpm-lock.yaml (regenerate with pnpm install; not hand-edited)
- src/steps/defs.ts (z.record single-argument form, only if needed for zod 4)
